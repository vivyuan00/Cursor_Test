# 数据采集、入仓与对账设计（ODS）

> **目标**：将核心平台、支付、WMS、CRM、企微等数据 **稳定、可核对** 地写入 ODS，支撑 T+1 DWD。  
> **关联**：[2026-05-14-数仓分层与主题域规范.md](./2026-05-14-数仓分层与主题域规范.md)

---

## 一、总体策略

| 数据源 | 推荐入仓方式 | 频率 | ODS 表命名（示例） |
|--------|--------------|------|---------------------|
| 核心平台业务库（MySQL 等） | **CDC（Debezium / Canal / 云 DTS）** 或 **按 `updated_at` 日增量** | 准实时或 T+1 | `ods_core_*` |
| 支付网关回调 / 支付流水表 | 业务库已落表则跟核心库；独立日志则 **日文件/API 拉取** | T+1 | `ods_pay_*` |
| 药房 WMS | API 回调落库后同步；或 **日批次导出** | T+1 为主 | `ods_wms_*` |
| CRM | 数据库同步或 **官方导出 SFTP** | T+1 | `ods_crm_*` |
| 企业微信 | **回调事件落库** + **会话存档批量** | 事件准实时 / 存档 T+1 | `ods_wework_*` |

**原则**：能进业务库的统一 **跟业务库 CDC**；孤岛系统 **先落中间表再入 ODS**，避免数仓直连外部 API 主链路。

---

## 二、核心库同步方案

### 2.1 CDC（首选）

- **捕获范围**：用户、角色、渠道、订单、处方、病历、对话主表、医助/医生维表等（表清单见 DWD 文档）。  
- **Initial load**：全量快照 + binlog 位点；首次按库分片并行。  
- **日常**：binlog 流写入 Kafka → 消费入 ODS 分区表 `pt=业务日` 或 `ingest_ts` 分区。  
- **幂等**：使用 `primary_key + op_type(u/c/d)` 或 **最新镜像覆盖**（按主键 merge）。

### 2.2 无 CDC 时的日增量（备选）

- **水位字段**：各表 `updated_at`（需索引）。  
- **抽取 SQL**：`where updated_at >= :last_watermark and updated_at < :batch_end`。  
- **删除行**：软删除用 `status`；物理删除需 **binlog** 或 **日全量 diff**（成本高，不推荐）。

### 2.3 分区与批次 ID

- 每批次生成 **`batch_id`**（UUID 或 `yyyymmddhhmmss`），写入 ODS 元数据表 `ods_batch_log`：源、行数、checksum、起止水位。  
- **业务分区 `pt`**：按 **业务日** 将变更归入对应分区（以 `updated_at` 转上海日期）；若跨日重跑需文档化 **「以事件日为准」** 规则。

## 三、支付数据

- **事实来源**：订单表 `payment_status`、`paid_at`、`paid_amount` 已与网关对账后落库 → **随核心库进 ODS**。  
- **独立对账文件**：若财务提供日对账单，增加 `ods_pay_reconcile_file_di`，字段：订单号、三方流水号、金额、状态；**对账任务**比对 `ods_core_order_di` 差异写入 `ads_reconcile_exception_di`（可选）。

---

## 四、WMS

- **事件**：接单、煎煮、发货、运单号、异常；以 **`order_no` / `order_id`** 关联。  
- **入 ODS**：`ods_wms_order_event_di`（一行一事件）或日镜像 `ods_wms_order_status_di`。  
- **对账**：日终 `count(*)`、`sum(amount)` 与平台订单侧 **已支付订单数** 交叉核对；差异阈值告警。

---

## 五、CRM

- **主键映射**：`crm_lead_id` ↔ `user_id` / `wework_id`；映射表必须在 ODS 保留 **`mapping_source`、`last_synced_at`**。  
- **同步方式**：优先 **CRM 数据库只读副本** 同步至 ODS；若无，用 **日增量 API**。  
- **对账**：用户数、标签变更条数与 CRM 报表 **抽样对账**（周）。

---

## 六、企业微信

| 数据类型 | 入 ODS 方式 | 用途 |
|----------|-------------|------|
| 添加/删除外部联系人回调 | 业务系统已落库则 CDC；否则 **回调日志表** 日增量 | 加微时间、**拉黑/删除关系** |
| 会话存档 | 定时拉取 JSON → `ods_wework_message_raw_di` | 首响时长、话术轮次（需 NLP 解析则下游 DWD） |

**拉黑医助**：以 **企微「客户删除员工 / 员工删除客户」回调** + 平台 `user.status` 一致性校验；冲突时优先级见 [专题集市文档](./2026-05-14-专题集市流失与拉黑.md)。

## 七、对账与质量校验（每日任务）

| 校验 ID | 描述 | 阈值示例 | 动作 |
|---------|------|----------|------|
| Q001 | ODS 核心订单行数 vs 生产 count | 差异 0 | 阻塞下游 |
| Q002 | `PAID` 订单 `paid_at` 非空率 | 100% | 告警 |
| Q003 | `user_id` 在订单中均存在于 user 表 | 100% | 告警 |
| Q004 | 企微回调日增量条数环比 | ±50% 外 | 人工复核 |
| Q005 | WMS 已发货但平台无运单号 | 0 | 告警 |

**元数据表（建议）**：

- `ods_batch_log`：批次、源、行数、状态。  
- `dwd_etl_quality_di`：规则 ID、异常条数、pt。

---

## 八、失败重试与回补

- 任务失败 **自动重试 3 次**（指数退避）。  
- **回补**：按 `pt` 重跑 ODS→DWD 链路；DWD 使用 **overwrite 分区** 保证幂等。  
- **回溯**：业务订正历史数据时，触发 **单 pt 或单主键重算** 工作流。
